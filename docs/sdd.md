# SDD 规约

## 1. 目标

moonset 采用 Specification-Driven Development（SDD）。规格文档是可评审、可追踪、可执行的产品契约，不是实现完成后的说明书。

每个需求都必须能回答四个问题：

1. 输入是什么，边界在哪里？
2. 成功时会观察到什么结果？
3. 失败时怎样报告，工作区会不会被修改？
4. 用哪个测试或命令证明它成立？

## 2. 追踪关系

```text
需求 ID -> 设计章节 -> 公共 API / CLI 契约 -> 测试编号 -> 验证命令
```

需求 ID 规则：

- `FR-*`：功能需求。
- `NFR-*`：质量、兼容性和可维护性需求。
- `SEC-*`：安全与权限需求。
- `API-*`：公共编程接口需求。
- `OPS-*`：CI、发布和运维需求。

## 3. 交付节奏

每个实现切片按以下顺序推进：

1. 把需求从 Proposed 改为 Accepted，补齐边界和验收条件。
2. 更新数据模型、命令契约或 ADR。
3. 先写纯函数测试，再接入文件系统、Git 或网络适配器。
4. 运行最窄验证，再运行 `moon check --target native` 和相关 `moon test`。
5. 更新需求状态、验证证据和已知限制。

## 4. 不可变原则

以下规则属于 v1 的设计不变量：

- 规划阶段不写工作区、不创建 Git 引用、不访问注册表。
- 执行前先完整解析并验证所有 changeset；任何一个文件无效，整个计划不执行。
- 版本和 changelog 写入采用临时文件加原子替换；执行失败不能留下半截文件。
- `publish` 不会隐式运行 `version`；发布前必须存在可审阅的 release commit，除非显式使用实验开关。
- 所有 Git 标签创建都可通过 `tag` 单独重试；标签格式在计划中固定并可预览。
- 机密只从环境或 GitHub OIDC/密钥注入，绝不写入 `.changeset` 文件、JSON 计划或日志。
